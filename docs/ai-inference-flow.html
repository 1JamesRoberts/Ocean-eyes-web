How OceanEyes AI inference currently works

This describes the current mobile prototype in the repository. The active live path runs the ONNX models inside the user’s browser. Camera frames are not uploaded to the FastAPI server during live detection or water-clarity measurement.

One-sentence summary: the app captures a video frame as a JPEG, sends the image Blob to a dedicated Web Worker, the worker runs ONNX Runtime Web locally, and the result is returned to React for overlays, readings, fish counts, and local history.

1. Full runtime flow

1

Camera starts

LiveFeedContext starts getUserMedia() for a webcam and binds the resulting MediaStream to the shared <video> element. The stream is kept alive while the user changes tabs.

↓
2

User enables AI Analysis

The Brain button calls toggleAI(). The check is named backendStatus, but it actually tests browser support for Worker, OffscreenCanvas, and createImageBitmap. It does not call the Python health endpoint.

↓
3

Polling captures one frame

useAIPolling runs immediately, then schedules the next pass after the configured interval (default: 10 seconds). It checks that the video has current data and real dimensions, draws the frame to a canvas, and converts it to a JPEG Blob at quality 0.92.

↓
4

React sends the Blob to the worker

detectFishOnDevice() posts a typed request containing an ID, the Blob, and the detection threshold (default: 0.35). The main thread keeps a map of pending requests so the matching Promise can resolve later.

↓
5

Worker loads models lazily

inference.worker.ts creates ONNX sessions only when first needed. Detection and turbidity use WASM; species classification prefers WebGPU and falls back to WASM. Requests are placed in a serial queue so only one inference operation runs at a time.

↓
6

Worker returns structured JSON

The worker decodes the Blob, runs the models, adds timestamps, original image dimensions, provider names, boxes, species, confidence values, and summary counts, then posts the result back to the main thread.

↓
7

UI and local data update

React stores the newest prediction. Bounding boxes and the analysis panel update; the feed’s fish count and reading update; and the result is appended to tank-scoped browser history in local storage. Analytics reads that local history directly.

2. What the detection worker does

A. Prepare the full frame

The original image is decoded with createImageBitmap. It is rendered to 576 × 576, converted from RGBA pixels to RGB, scaled to 0–1, ImageNet-normalized, and rearranged into an ONNX NCHW tensor: [1, 3, 576, 576].

fish_detection.onnxWASM

B. Find fish boxes

The detector returns box values and class logits. For each query, the worker takes the highest logit, applies a sigmoid, and discards detections below the selected threshold. Center-format boxes are converted to pixel coordinates in the original image and clipped to its edges.

C. Classify each crop

Every accepted box is cropped from the original frame, resized to 255 × 255, center-cropped to 224 × 224, ImageNet-normalized, and sent to the species model. Softmax selects the highest-probability species. Species confidence below 0.30 is represented as below_threshold: true and counted as unknown.

species_classifier.onnxWebGPU → WASM

D. Build the result

Each detection contains bbox, bbox_normalized, detection confidence, species ID/display name, species confidence, threshold state, and diagnosis: null. The summary contains total detections and counts by species.

3. What the turbidity worker does

Turbidity is not part of the repeating fish-detection loop. It runs when the user presses the water-clarity button.

Input

The same video-to-JPEG capture is used. The worker renders the full image to 224 × 224, scales RGB values to 0–1, and creates an ONNX tensor shaped [1, 3, 224, 224].

Output

The model returns probabilities for 11 turbidity classes. The worker calculates FNU using the configured linear formula:

FNU = -60.9 + Σ(class probability × class coefficient)

It also returns the top class, top confidence, and all probabilities.

Lifecycle

The turbidity ONNX session is released after each measurement. The next measurement loads it again. This is different from the detection and species sessions, which remain cached in the worker.

5. Model delivery

The browser model paths are /models/fish_detection.onnx, /models/species_classifier.onnx, and /models/turbidity.onnx. The Vite plugin serves the web models during development and copies them into dist/models during a production build. Before copying, it verifies the expected byte size and SHA-256 hash from ai/models/model-manifest.json.

Models are requested lazily by the worker and cached by the browser. A version query parameter (2026-07-15-v3) is added to the model URL to invalidate stale cached models when the configured model version changes.

6. Cancellation, errors, and limitations

Cancellation

Stopping AI clears the next timer and aborts the current request. Unmounting the live hook does the same. Worker errors reject all pending requests and recreate the worker on the next request.

No cloud fallback

If the browser lacks the required on-device APIs, the controls report that on-device AI is unavailable. The current live hooks do not switch over to the FastAPI service.

Disease diagnosis

The on-device result sets diagnosis to null, and the diagnosis control is disabled in the prototype. The Python backend contains an optional LLM diagnosis path, but it is not part of this active browser flow.

Persistence detail

Each inference is added to local history immediately. The most recent full prediction/turbidity object is also copied into live state when the stream stops, so it can be restored later.

7. The retained FastAPI backend

Important distinction: the repository still contains the server implementation, but the current frontend does not call it for live inference.

The server continues to expose POST /predict/detection and POST /predict/turbidity for direct integration clients. Those requests run through the Python FishAIPipeline, ONNX Runtime for Python, and return JSON responses.

FastAPI loads its models once at startup and prefers CUDA, then DirectML, then CPU. It also writes server-side JSONL history. That server route is useful legacy/integration code, but current browser polling uses detectFishOnDevice() and current turbidity measurement uses measureTurbidityOnDevice().
